# Plan: Multi-node Raft with TLS (goca-issued internal PKI) + StatefulSet discovery

- **Module:** `github.com/disaster/dagger-kubernetes`
- **Working dir:** `/projects/dagger-cache`
- **Go version:** `go 1.26.5` (from `go.mod`)
- **Scope:** Upgrade the Raft store (ADR-015) from a single-node plaintext-TCP
  deployment to a **multi-node, TLS-secured** Raft cluster whose peers are
  discovered from a Kubernetes StatefulSet's stable pod DNS names, with
  internal certificates generated by `github.com/disaster37/goca`. The FSM,
  command set, repository layer, domain interfaces, and HTTP error mapping are
  **unchanged**. Single-node remains a degenerate case (`replicas=1`).
- **Builds on:** `.opencode/plans/raft-replace-sqlite.md` (already landed).
  This plan closes the four known gaps called out in that plan's review:
  1. Raft transport is plaintext TCP; `raft.tls.enabled` is inert.
  2. `raft.bind_addr: ":8081"` advertises `127.0.0.1`, breaking multi-node.
  3. The Helm chart ships a `Deployment`, not a StatefulSet + headless Service.
  4. `cmd/api/main.go` treats `WaitForLeader` as a hard startup barrier
     (non-leaders exit), contradicting ADR-015 D5 (stale reads on followers).

## 1. Summary & architectural overview

### 1.1 What changes

- **TLS transport**: the Raft `StreamLayer` is wrapped in `crypto/tls` (TLS 1.2+,
  mTLS — peers present a cert and verify each other against a shared internal
  CA). Plaintext remains available for single-node dev/test
  (`raft.tls.enabled=false`), but the Helm chart enables TLS by default.
- **Internal PKI (goca)**: a self-signed internal CA is generated with
  `github.com/disaster37/goca` and shared across pods; each pod issues itself a
  per-node leaf certificate (server+client auth) with SANs covering its stable
  pod DNS names + `127.0.0.1`. CA + leaf are persisted under
  `<database.dir>/tls/` and reused across restarts.
- **StatefulSet discovery**: peers are derived from the StatefulSet's stable pod
  DNS names (`<sts>-<i>.<headless>.<ns>.svc.cluster.local:8081` for
  `i=0..replicas-1`) — pure DNS arithmetic, **no K8s API calls, no new RBAC**.
  An explicit `raft.peers` override is kept for non-K8s/testing.
- **Advertise address**: each node advertises its pod FQDN (derived from
  `os.Hostname()` + headless service + namespace + port), not `127.0.0.1`.
- **Follower startup**: the hard `WaitForLeader` barrier is replaced. Every node
  waits until **a** leader exists (not necessarily itself). The leader
  provisions the JWT secret + token-encryption key (idempotent); followers wait
  for those meta keys to replicate to the local FSM, then serve stale reads and
  return `ErrNotLeader` (503) on writes — ADR-015 D5.
- **Helm chart**: `Deployment` → `StatefulSet` with `volumeClaimTemplates`
  (per-pod PVC), a new **headless Service** for stable pod DNS + the raft port,
  `podManagementPolicy: Parallel`, and TLS env wiring. The existing
  `<release>-control` and `<release>-data` Services stay (ClusterIP, select all
  Ready pods).

### 1.2 TLS PKI layout

```
<database.dir>/tls/
  ca.crt            # internal raft CA cert (PEM)        0600  (shared via K8s Secret in auto-mode)
  ca.key            # internal raft CA key  (PEM)        0600  (shared via K8s Secret in auto-mode)
  node.crt          # this pod's leaf cert  (PEM)        0600  (per-pod, SANs = pod DNS + 127.0.0.1)
  node.key          # this pod's leaf key   (PEM)        0600  (per-pod)
```

The CA is **shared** across all pods (so peers trust each other's leaf certs).
Three modes, selected by config:

| Mode | Trigger | CA distribution |
|---|---|---|
| **Auto (K8s)** | `raft.tls.enabled=true`, no manual cert paths, K8s clientset available, `raft.tls.ca_secret` set | Pod with ordinal 0 (`os.Hostname()` ends in `-0`, or `raft.tls.ca_bootstrap=true`) generates the CA via goca and writes it to a K8s Secret `<raft.tls.ca_secret>`; other pods poll the secret (bounded by `raft.leader_wait_timeout`) before issuing their leaf. |
| **Manual** | `raft.tls.ca_cert` + `raft.tls.cert` + `raft.tls.key` all set | Operator pre-provisions CA + leaf (e.g. cert-manager, external). No auto-generation, no K8s Secret. |
| **Local-only (single-node dev/test)** | `raft.tls.enabled=true`, no manual paths, no K8s clientset | The node generates a CA + its own leaf locally. **Multi-node is rejected** in this mode (error: "raft TLS auto-mode requires K8s or manual CA files for multi-node"). |

Rationale for the K8s-Secret approach (vs a Helm `pre-install` hook Job): it is
fully automatic for any deploy (not just Helm), needs no extra subcommand or
hook image, and the supervisor already holds a K8s clientset + secret RBAC
(`rbac.yaml` already grants `secrets create/update/get/list/watch`).
`podManagementPolicy: Parallel` lets all pods boot concurrently; the
non-bootstrap pods' bounded poll handles the startup race. The Helm-hook
alternative is documented in §10 as a simpler-but-less-general option.

### 1.3 StatefulSet topology

- **StatefulSet** `<release>-supervisor` (name from `raft.statefulset_name`,
  defaulted by the chart to the StatefulSet name), `podManagementPolicy:
  Parallel`, `serviceName: <release>-headless`.
- **Headless Service** `<release>-headless` (`clusterIP: None`), exposing the
  raft port `8081`. Pod FQDN: `<sts>-<i>.<release>-headless.<ns>.svc.cluster.local`.
- **Control Service** `<release>-control` (ClusterIP, port 80→8080) — unchanged.
- **Data Service** `<release>-data` (ClusterIP, port 443→8443) — unchanged.
- **PVC**: moved from `templates/pvc.yaml` into the StatefulSet
  `volumeClaimTemplates` (per-pod, `ReadWriteOnce`). `pvc.yaml` is deleted.
- **RBAC**: no change. DNS-arithmetic discovery needs no K8s API; the CA-secret
  write reuses the existing `secrets` verbs in `rbac.yaml`.

### 1.4 Bootstrap scenarios

- **First boot of a 3-node cluster**: all 3 pods boot (Parallel). Pod-0
  generates the CA, writes the K8s Secret, issues its leaf, starts its TLS
  transport, and bootstraps the cluster with all 3 voters. Pods 1/2 poll the
  secret, then issue leaves, start transports, and join. Raft elects a leader;
  the leader provisions meta; followers receive meta via replication and become
  Ready.
- **Scale-up 1→3**: bump `replicaCount` 1→3 + `raft.replicas` 1→3; rolling
  restart (pods re-read `raft.replicas`). The existing node's data dir already
  has state, so `BootstrapCluster` returns `ErrCantBootstrap` (ignored); the new
  voters join via the bootstrap configuration. **Note**: hashicorp raft's
  `BootstrapCluster` only seeds the initial configuration; adding voters to a
  running cluster requires `raft.AddVoter`. See §6 (scale-up) — this plan
  implements `AddVoter`-based join for scale-up, not just re-bootstrap.
- **Restart**: each pod reuses its `<dir>/node-id`, `<dir>/tls/*`, and
  `<dir>/raft.db`. The CA secret already exists; pods read it. The cluster
  re-elects a leader.
- **Single-node (`replicas=1`)**: degenerate case. Pod-0 generates the CA +
  leaf, bootstraps with itself as the only voter, becomes leader, provisions
  meta. Identical to today's behavior plus TLS.

## 3. Data structures & function signatures (new code)

### 3.1 `internal/repository/raft_discovery.go`

```go
package repository

// RaftPeer is one voter in the cluster configuration (unchanged struct,
// restated here for the resolver contract).
type RaftPeer struct {
    ID      string
    Address string // host:port
}

// PeerResolver computes the full voter list for bootstrap/join and identifies
// this node's own peer entry.
type PeerResolver interface {
    // Resolve returns the full ordered voter list (including self).
    Resolve() ([]RaftPeer, error)
    // Self returns this node's peer entry (by ID or advertise address).
    Self() (RaftPeer, error)
}

// NewPeerResolver selects a resolver from config:
//   - if cfg.Peers is non-empty → staticPeerResolver (explicit override).
//   - else if cfg.StatefulSetName != "" && cfg.HeadlessService != "" → dnsPeerResolver.
//   - else → singleNodeResolver (self only, from cfg.AdvertiseAddr/BindAddr).
func NewPeerResolver(cfg RaftDiscoveryConfig) (PeerResolver, error)

// RaftDiscoveryConfig is the subset of RaftConfig driving discovery.
type RaftDiscoveryConfig struct {
    NodeID          string
    AdvertiseAddr   string // host:port; "" = derive from hostname+headless+port
    BindAddr        string // host:port (fallback for advertise derivation)
    Peers           []RaftPeer
    Replicas        int
    StatefulSetName string
    HeadlessService string
    Namespace       string
    RaftPort        int // from bind_addr; default 8081
}

// dnsPeerResolver derives peers from <sts>-<i>.<headless>.<ns>.svc.cluster.local.
type dnsPeerResolver struct {
    cfg RaftDiscoveryConfig
    // clusterDomain is "cluster.local" (configurable via cfg, default
    // "cluster.local"); resolved once at construction.
    clusterDomain string
}

func (r *dnsPeerResolver) Resolve() ([]RaftPeer, error)
func (r *dnsPeerResolver) Self() (RaftPeer, error)

// staticPeerResolver returns the explicit raft.peers list.
type staticPeerResolver struct {
    peers []RaftPeer
    self  RaftPeer // matched by NodeID or AdvertiseAddr
}

func (r *staticPeerResolver) Resolve() ([]RaftPeer, error)
func (r *staticPeerResolver) Self() (RaftPeer, error)

// deriveAdvertiseAddr computes this pod's advertise address:
//   - cfg.AdvertiseAddr if set.
//   - else if hostname matches <sts>-<ordinal>: "<hostname>.<headless>.<ns>.svc.<clusterDomain>:<port>".
//   - else: the bind host (warn if 127.0.0.1/0.0.0.0 with multi-node).
func deriveAdvertiseAddr(cfg RaftDiscoveryConfig, hostname string) (string, error)

// podSANs returns the DNS + IP SANs for this pod's leaf cert:
//   DNS: <hostname>, <hostname>.<headless>, <hostname>.<headless>.<ns>,
//        <hostname>.<headless>.<ns>.svc, <hostname>.<headless>.<ns>.svc.<clusterDomain>,
//        "localhost"
//   IP:   127.0.0.1
func podSANs(cfg RaftDiscoveryConfig, hostname string) (dnsNames []string, ipAddrs []net.IP)
```

### 3.2 `internal/repository/raft_tls.go`

```go
package repository

import (
    "crypto/tls"
    "crypto/x509"
    "net"
    "os"
    "time"

    "github.com/disaster37/goca"
    "k8s.io/client-go/kubernetes"
)

// RaftTLSConfig is the TLS subset of domain.RaftConfig, passed to the builder.
type RaftTLSConfig struct {
    Enabled      bool
    Dir          string        // default <database.dir>/tls
    Validity     time.Duration // default 8760h (1y)
    Organization string        // default "dagger-cache-raft"
    CACertPath   string        // manual mode: CA cert file
    CertPath     string        // manual mode: leaf cert file
    KeyPath      string        // manual mode: leaf key file
    CASecret     string        // auto/K8s mode: K8s Secret name for CA sharing
    CABootstrap  bool          // auto/K8s mode: this node generates+writes the CA
    ClientAuth   bool          // default true (mTLS)
}

// raftTLSMaterial is the loaded CA + leaf used to build the transport tls.Config.
type raftTLSMaterial struct {
    caCertPEM   []byte
    caKeyPEM    []byte // not needed at runtime after leaf issuance, but kept for re-issue
    leafCertPEM []byte
    leafKeyPEM  []byte
    caPool      *x509.CertPool
    leaf        tls.Certificate
}

// loadOrBuildRaftTLS prepares the raft TLS material per the selected mode:
//   - manual: load CA + leaf from the configured paths.
//   - auto/K8s: ensure the CA Secret exists (bootstrap node creates it via
//     goca), read it, then issue/reuse this node's leaf at <dir>/tls/node.*.
//   - local-only: generate CA + leaf locally (single-node only).
// Returns the material + the tls.Config for the raft StreamLayer.
func loadOrBuildRaftTLS(
    cfg RaftTLSConfig,
    isMultiNode bool,
    clientset kubernetes.Interface,
    namespace string,
    dnsNames []string,
    ipAddrs []net.IP,
    commonName string,
    logger *logrus.Logger,
) (*raftTLSMaterial, *tls.Config, error)

// ensureRaftCA returns the CA cert+key PEM, creating it on the bootstrap node
// and sharing via a K8s Secret, or loading from disk in manual/local mode.
func ensureRaftCA(
    cfg RaftTLSConfig,
    clientset kubernetes.Interface,
    namespace string,
    logger *logrus.Logger,
) (caCertPEM, caKeyPEM []byte, err error)

// createRaftCAWithGoca builds a new self-signed CA via goca and returns PEM
// cert+key. Uses the exact API already used in ca_providers.go:
//   goca.Identity{Organization, OrganizationalUnit, Country, Locality, Province}
//   goca.New(name string, identity goca.Identity) (*goca.CA, error)
//   (*goca.CA).GetCertificate() string  // PEM
//   (*goca.CA).GetPrivateKey() string  // PEM
func createRaftCAWithGoca(name, organization string) (certPEM, keyPEM []byte, err error)

// issueOrReuseNodeCert issues a per-node leaf cert signed by the CA (loaded
// into a *MintingCA via NewMintingCAFromPEM) with the given DNS + IP SANs,
// persisted at <dir>/tls/node.crt + node.key (0600). Reused if present and
// not expired. Uses MintingCA.IssuePeerCertificate (new method in ca.go).
func issueOrReuseNodeCert(
    cfg RaftTLSConfig,
    ca *MintingCA,
    commonName, organization string,
    dnsNames []string,
    ipAddrs []net.IP,
) (certPEM, keyPEM []byte, err error)

// buildRaftTLSConfig assembles the *tls.Config for the raft StreamLayer:
//   Certificates: [leaf]
//   RootCAs: caPool, ClientCAs: caPool
//   ClientAuth: RequireAndVerifyClientCert (when ClientAuth=true) else NoClientCert
//   MinVersion: TLS1.2, NextProtos: [] (none)
func buildRaftTLSConfig(m *raftTLSMaterial, clientAuth bool) *tls.Config

// tlsStreamLayer implements raft.StreamLayer over a TLS-wrapped net.Listener.
type tlsStreamLayer struct {
    listener net.Listener
    config   *tls.Config
}

func newTLSStreamLayer(bindAddr string, advertise net.Addr, config *tls.Config) (*tlsStreamLayer, net.Addr, error)
func (l *tlsStreamLayer) Accept() (net.Conn, error)   // tls.Server(c, l.config)
func (l *tlsStreamLayer) Dial(addr raft.ServerAddress, timeout time.Duration) (net.Conn, error) // tls.Dial("tcp", string(addr), l.config)
func (l *tlsStreamLayer) Close() error
func (l *tlsStreamLayer) Addr() net.Addr
```

**goca API used (exact, verified against `internal/repository/ca_providers.go`):**

```go
identity := goca.Identity{
    Organization:       organization,            // e.g. "dagger-cache-raft"
    OrganizationalUnit: "engineering",
    Country:            "US",
    Locality:           "San Francisco",
    Province:           "California",
}
caInstance, err := goca.New("dagger-cache-raft-ca", identity)
if err != nil { return nil, nil, fmt.Errorf("create goca CA: %w", err) }
certPEM := []byte(caInstance.GetCertificate()) // PEM string
keyPEM := []byte(caInstance.GetPrivateKey())    // PEM string
```

> **Note for the coder:** `goca.New` + `.GetCertificate()` + `.GetPrivateKey()`
> is the exact pattern already used in `ca_providers.go` (`createCA`). Leaf
> signing is done by the project's own `MintingCA` (stdlib `crypto/x509`),
> loaded from the goca-generated CA PEM via `NewMintingCAFromPEM` — this is the
> established codebase convention. Run `go doc github.com/disaster37/goca` to
> confirm whether goca exposes direct leaf-issuance helpers; if so and they
> simplify the code, they may be used, but the `MintingCA` path is preferred for
> consistency with `ca_providers.go`.

## 4. Edge cases & failure modes

- **Cert regeneration/renewal**: leaf certs are reused if present and
  `NotAfter > now+<safety margin (e.g. 7d)>`. If expired or within the margin,
  re-issue from the CA (CA material is still present). The supervisor logs the
  re-issue. A future knob (`raft.tls.rotate_before`) can tune the margin; v1
  uses a fixed 7d margin.
- **Certificate rotation without downtime**: re-issuing a leaf cert happens at
  startup. For in-place rotation, an operator can delete `<dir>/tls/node.*` and
  restart the pod; the new cert is signed by the same CA and trusted by all
  peers immediately. CA rotation (replacing the CA) is **out of scope** for v1
  (requires distributing a new CA + bumping leaf certs across all pods); the
  CA has a 10-year NotAfter (goca default), so this is a long-term concern.
- **CA + cert persistence & permissions**: `<dir>/tls/` is created `0700`;
  `ca.crt`/`ca.key`/`node.crt`/`node.key` are written `0600` (matches the
  existing `node-id`/`raft.db`/`snapshots/` hardening in `raft_store.go`).
- **First-boot 3-node bootstrap**: see §1.4. Pod-0 writes the CA Secret; pods
  1/2 poll (bounded by `leader_wait_timeout`, default 30s). If pod-0 fails to
  write the secret within the bound, pods 1/2 exit with a clear error; pod-0's
  own error propagates. K8s restarts pod-0; the retry succeeds.
- **Scale-up 1→3**: bumping `replicaCount`+`raft.replicas` and rolling-restarting
  is NOT sufficient on its own — `BootstrapCluster` only seeds the initial
  voter set and returns `ErrCantBootstrap` for a node with existing state. The
  **leader** must call `raft.AddVoter(newID, newAddr)` for each new pod. The
  supervisor implements a `joinLoop` goroutine: after `WaitForLeader`, if the
  resolver's voter list is larger than the current raft configuration, the
  leader calls `AddVoter` for each missing voter (idempotent; `AddVoter` on an
  existing voter is a no-op). Followers do nothing (the leader drives join).
  This handles scale-up without manual `raft.AddVoter` CLI.
- **Scale-down**: shrinking `replicaCount`+`raft.replicas` requires the leader
  to call `raft.RemoveServer` for the removed ordinals. v1 implements
  `RemoveServer` in the same `joinLoop` (the leader removes voters absent from
  the resolver's list). **Caveat**: removing a voter that is still running
  causes that pod to log `not in configuration` errors; the operator must
  delete the pod after scaling down. Documented.
- **Node replacement**: a pod that loses its `<dir>/node-id` becomes a new
  node. The operator must remove the old voter (`raft.RemoveServer`) and let
  the new pod join (`AddVoter`). v1's `joinLoop` handles the `AddVoter` side;
  `RemoveServer` for a dead node is triggered by the resolver no longer listing
  the old ID (the old PVC is gone, so the old ID never reappears). Documented
  operational note.
- **Split-brain / leadership**: Raft's quorum guarantee prevents split-brain.
  A 2-node cluster has no failure tolerance (loses quorum on 1 failure); the
  chart defaults `replicaCount: 3` for multi-node. A 1-node cluster is always
  available (single voter). Documented.
- **TLS handshake failures**: a peer presenting an untrusted cert (wrong CA)
  or a cert with no matching SAN is rejected by `tls.Dial`/`tls.Server`. The
  raft transport logs the handshake error and drops the connection; raft
  retries. The supervisor logs at WARN with the peer address.
- **Hostname/SAN verification**: `tls.Dial` sets `ServerName` to the host part
  of the dial address (the peer's pod FQDN), which must match a SAN on the
  peer's leaf cert. `podSANs` includes the full FQDN, the short hostname, and
  intermediate forms, so any of the resolver's dial addresses verifies.
- **Certificate expiry**: an expired leaf cert causes handshake failure. The
  supervisor checks `NotAfter` at startup and re-issues; mid-life expiry is
  caught on the next restart. A future enhancement can add a background
  re-issue timer (out of scope for v1).
- **Mixed TLS/plaintext**: a node with `raft.tls.enabled=true` cannot talk to a
  node with `raft.tls.enabled=false` (handshake vs. plaintext). The chart sets
  `raft.tls.enabled` uniformly across all pods (single configmap), so this
  cannot happen in a Helm deploy. For non-Helm deploys, the operator must set
  it uniformly; the supervisor logs a WARN if any resolved peer's scheme
  differs (best-effort; not enforced since raft addresses carry no scheme).
- **Clock skew**: TLS `NotBefore`/`NotAfter` use the local clock. A pod with a
  skewed clock >5min behind the CA's clock may reject certs (`NotBefore` in the
  future). Mitigation: the CA sets `NotBefore = now - 5min` (clock-skew
  tolerance, standard practice). Documented.
- **Node-id stability**: unchanged from ADR-015 — `<dir>/node-id` is `0600` on
  the PVC, reused across restarts. A node that loses it becomes a new node
  (see "Node replacement").

## 5. Error handling & validation

- **Config validation** (in `cmd/api/main.go` before `NewRaftStore`):
  - If `raft.tls.enabled=true` and any of `raft.tls.ca_cert`/`cert`/`key` is
    set, **all three** must be set (manual mode) → else `fmt.Errorf("raft.tls: ca_cert/cert/key must all be set together")`.
  - If `raft.tls.enabled=true` and manual paths are unset and `raft.replicas > 1`
    and `raft.tls.ca_secret == ""` and no K8s clientset → error: "raft TLS
    auto-mode for multi-node requires K8s or manual CA files".
  - If `raft.replicas > 1` and `raft.statefulset_name == ""` and
    `raft.peers` is empty → error: "raft multi-node requires statefulset_name
    or explicit peers".
  - If `raft.advertise_addr` resolves to `127.0.0.1`/`0.0.0.0` and
    `raft.replicas > 1` → error: "raft.advertise_addr must be routable for
    multi-node".
- **TLS load/parse errors**: `loadOrBuildRaftTLS` wraps PEM-decode / x509-parse
  / key-parse errors with `%w` and a label; the supervisor fails to start with
  a clear message (e.g. "raft TLS: parse CA cert: ...").
- **Discovery failures**: `dnsPeerResolver.Resolve` validates `replicas >= 1`,
  `statefulset_name != ""`, `headless_service != ""`, `namespace != ""`; else
  returns a wrapped error. `Self()` returns an error if the hostname does not
  match `<sts>-<ordinal>` and `advertise_addr` is unset.
- **CA Secret write/read failures**: wrapped with `%w`; the bootstrap node
  fails to start if it cannot create the secret; non-bootstrap nodes fail if
  the secret does not appear within `leader_wait_timeout`.
- **Error → HTTP mapping**: unchanged. `ErrNotLeader`→503, `ErrRaftTimeout`→504
  (already in `internal/handler/middleware.go`). No new sentinels. The
  follower-startup path does not introduce new HTTP errors (followers serve
  reads normally; writes return `ErrNotLeader` as today).

## 6. Startup flow (cmd/api/main.go)

```
1. Load config; validate (§5).
2. Build PeerResolver from raft config (NewPeerResolver).
3. Resolve self + full voter list.
4. If raft.tls.enabled:
     dnsNames, ipAddrs = podSANs(raftCfg, hostname)
     tlsMaterial, tlsConfig = loadOrBuildRaftTLS(raftCfg.TLS, isMultiNode,
         clientset, namespace, dnsNames, ipAddrs, commonName=selfID, logger)
   else:
     tlsConfig = nil
5. raftStore = NewRaftStore(RaftStoreConfig{
        Dir, NodeID, BindAddr, AdvertiseAddr, Resolver, ..., TLS: tlsConfig,
   }, logger)
6. leaderCtx, cancel := context.WithTimeout(ctx, raft.LeaderWaitTimeout)
   err := raftStore.WaitForLeader(leaderCtx)   // ANY leader exists
   cancel()
   if err != nil: return err
7. metaStore = NewMetaStore(raftStore)
   if raftStore.IsLeader():
       jwtSecret = loadOrCreateJWTSecret(...)   // Set works (leader)
       tokenEncKey = loadOrCreateTokenEncryptionKey(...)
   else:
       jwtSecret = waitForMetaSecret(ctx, metaStore, "jwt_secret",
           raft.LeaderWaitTimeout, logger)   // poll Get until present
       tokenEncKey = waitForMetaSecret(ctx, metaStore, "token_encryption_key", ...)
8. go observeLeadership(ctx, raftStore, logger)
9. go joinLoop(ctx, raftStore, resolver, logger)   // AddVoter/RemoveServer on leader
10. ... (rest unchanged: repos, services, server.Start, etc.)
```

`waitForMetaSecret` polls `metaStore.Get(key)` every 500ms until it returns a
value or `ctx` expires; on expiry returns a wrapped error. It reads from the
local FSM (stale reads are fine here — the value, once replicated, is stable).

`joinLoop` (leader only): periodically (e.g. every 5s) compares the resolver's
voter list to `raftStore.raft.GetConfiguration().Configuration().Servers`; calls
`AddVoter` for missing voters and `RemoveServer` for extra voters. Stops on
`ctx.Done()`. Logs at INFO.

`migrate-tokens` (runMigrateTokens): replace `WaitForLeader` with
`WaitForSelfLeadership` (it must write). Documented: `migrate-tokens` assumes
single-node operation; for multi-node, run it against a running leader via the
API, or scale the cluster to 1 first. (Pre-existing limitation; not introduced
by this change.)

## 11. Risks, trade-offs, open questions

### Risks

- **R1 — CA Secret write race / pod-0 failure.** If pod-0 fails before
  writing the CA Secret, pods 1/2 block on the poll and eventually exit. K8s
  restarts pod-0; the retry succeeds. *Mitigation*: bounded poll +
  `podManagementPolicy: Parallel` (all pods retry together); documented.
- **R2 — `AddVoter`/`RemoveServer` joinLoop complexity.** The joinLoop adds
  operational nuance (scale-up needs the leader to add voters; scale-down needs
  `RemoveServer` + pod deletion). *Mitigation*: documented runbook in the helm
  README; the joinLoop is leader-only and idempotent.
- **R3 — Stale reads + 503 on writes behind a load-balanced Service.** The
  control/data Services select all Ready pods; a write may hit a follower
  (503) and require a client retry. *Mitigation*: acceptable for RBAC write
  frequency; documented. Future: a `Leader-Address` header in the 503, or a
  leader-only Service via a `raft-leader` pod label.
- **R4 — 2-node cluster has no failure tolerance.** *Mitigation*: chart
  default `replicaCount: 3`; documented.
- **R5 — CA rotation out of scope.** The CA has a 10-year life (goca default);
  CA replacement is a future operational task. *Mitigation*: documented.
- **R6 — `migrate-tokens` with multi-node.** It opens its own Raft node and
  must write; with multi-node it cannot reach quorum alone. *Mitigation*:
  documented (run against a running leader via the API, or scale to 1 first).
  Pre-existing limitation.
- **R7 — TLS hostname verification on dial.** `tls.Dial` uses the dial
  address host as `ServerName`; the resolver must dial addresses that match a
  SAN on the peer's leaf. *Mitigation*: `podSANs` includes all FQDN forms;
  tested in `newThreeNodeTLSRaftCluster`.

### Trade-offs

- **DNS-arithmetic vs K8s API discovery.** Chose DNS-arithmetic: no RBAC, no
  API dependency at startup, deterministic, matches the etcd/consul model.
  Trade-off: scale-up requires a rolling restart (pods re-read `raft.replicas`)
  + the `AddVoter` joinLoop. The K8s-API alternative would auto-detect new pods
  but couples raft startup to the API and needs StatefulSet get/list RBAC.
- **K8s-Secret CA sharing vs Helm pre-install hook.** Chose K8s-Secret: works
  for any deploy, no hook Job, no extra subcommand. Trade-off: pod-0
  special-casing + bounded poll. The Helm-hook alternative (a `pre-install`
  Job running `supervisor raft-init-ca`) is simpler for Helm-only deploys but
  adds a subcommand + hook image.
- **goca for CA + stdlib `MintingCA` for leaf vs goca end-to-end.** Chose the
  existing codebase convention (goca for CA creation, `MintingCA` for leaf
  signing) for consistency with `ca_providers.go`. Trade-off: two code paths;
  justified by reuse.
- **Follower stale reads vs leader-only serving.** Chose stale reads
  (ADR-015 D5): keeps read performance, matches single-node behavior. Trade-off:
  followers can return slightly stale data + 503 on writes. The alternative
  (leader-only serving, followers refuse all traffic) wastes follower capacity
  and contradicts D5.
- **`podManagementPolicy: Parallel` vs `OrderedReady`.** Chose `Parallel` so
  all pods boot concurrently and can elect a leader (a 3-node cluster cannot
  form quorum with `OrderedReady` since pod-0 alone has no quorum). Trade-off:
  the CA-Secret poll handles the startup race instead of `OrderedReady`
  ordering.

### Open questions (resolved with recommended answers)

- **OQ1 — Should the control/data Services route only to the leader?**
  Recommended: **No (v1).** Keep selecting all Ready pods; followers serve
  stale reads + 503 on writes; clients retry. A leader-only Service (via a
  `raft-leader` pod label) is a future enhancement.
- **OQ2 — Should `joinLoop` also handle `DemoteVoter` for graceful
  scale-down?** Recommended: **No (v1).** `RemoveServer` is sufficient;
  `DemoteVoter` is a future refinement for zero-quorum-loss scale-down.
- **OQ3 — Should the raft CA be the same as the minting CA (`tls.ca_path`)?
  Recommended: **No.** Separate CA under `<database.dir>/tls/` — the raft CA
  is cluster-internal and shared via K8s Secret; the minting CA is for engine
  client certs and already has its own lifecycle. Keeping them separate avoids
  coupling.
- **OQ4 — Should `raft.tls.enabled` default to `true` in the binary?**
  Recommended: **No.** Binary default `false` preserves single-node dev/test
  simplicity (no CA generation needed). The Helm chart sets it `true`.
- **OQ5 — Should discovery support a K8s-API mode as a fallback when DNS
  arithmetic is undesirable?** Recommended: **No (v1).** DNS-arithmetic is
  sufficient; K8s-API mode is a future enhancement (would need StatefulSet
  get/list RBAC + a readiness-aware resolver).
